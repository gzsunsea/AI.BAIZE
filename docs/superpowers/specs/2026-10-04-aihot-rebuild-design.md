## 方案选择

**推荐：完整替换前端，直接复用 AIHOT 的页面和视觉实现，为 AI.BAIZE 现有采集数据实现接口适配。** 新站从独立目录与分支建立，旧 UI 不参与新站渲染。保留已有采集、评分、运行数据和认证能力，通过新接口提供新页面需要的数据。此方案最直接对应用户列出的 UI、信息架构、布局、视觉与交互重建范围；需要明确记录无法由已有数据支撑的交互，不编造热度、趋势、模型榜或全文。

备选：整体迁入 AIHOT 的前端、API、Worker 和 PostgreSQL。优点是框架一致；代价是 Node 升级、数据库迁移、历史数据映射及采集管线重新验证，并需要处理模型服务配置。未经授权不引入付费服务，也不自动开启外部推送。此方案需要额外的数据迁移设计，不能直接覆盖生产目录。

不采用在现有组件上逐块调整样式的路径，因为不符合本次独立重建要求。

## 数据与交互边界

- 前端只经 HTTP 访问站点接口，不读取数据库或密钥。
- 接口适配应覆盖数据字段、筛选、分页、详情、报告归档、反馈与管理认证；不能以空数组掩盖适配遗漏。
- 按对标实现返回位置恢复、浏览器前后导航、收藏持久化、日组折叠、手机搜索/筛选弹层、图片预览、明暗/系统主题切换。
- 用户操作涉及写入时复用现有权限边界。不会因 UI 重建自动启用 MCP、付费模型或外部通知。
- 条款和隐私页面需根据实际实现写成可审核文本；上游模板不是本站事实，不直接照搬。

## 发布顺序与回滚

1. 保存当前本地未提交工作为 Git 快照，建立重建分支，并记录生产版本、代码包和独立数据备份。
2. 在独立目录完成新前端和接口适配，补齐上游全代码审读记录与许可证清单。当前只完成部分核心文件审读，不能声称全仓库审读完成。
3. 本地完成构建、类型检查、相关回归和浏览器功能/响应式/视觉审查。
4. 生产服务器部署独立候选版本，用独立端口验证；保留旧站正在运行的目录和服务。
5. 候选通过后切换域名入口，检查首页、真实内容、详情、报告、后台认证及所有构建资源。
6. 线上验证通过后，从新版本活动代码中删除旧前端及废弃页面，不保留可访问旧版入口；Git 历史和回滚包保留。数据库和秘密配置不作为旧 UI 删除。
7. 记录删除提交和线上验证时间。若任何门槛失败，保持或恢复旧生产版本。
