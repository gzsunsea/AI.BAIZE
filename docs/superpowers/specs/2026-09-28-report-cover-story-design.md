# AI.BAIZE 报告头版主稿设计

日期：2026-09-28
状态：设计草案，待用户复核
范围：日报、周报、月报增加自动头版主稿；不包含编辑后台、采集改造或生产部署

## 背景与目标

AIHOT 2026-09-28 更新说明将报纸式报告的“头版头条和配图”列为日报、周报、月报的改版内容。AI.BAIZE 已有期刊抬头、摘要、栏目、按期导航、事件去重及来源信息，但没有从报告文章中单独呈现头版主稿。

目标是在不改变报告现有精选集合与顺序的前提下，为读者提供一个可直接打开的代表性故事；若该文章有可用图片则展示同一文章的配图，无图时自然退化为文字主稿。头版主稿是自动选出的“代表稿”，不冒称人工编辑选出的绝对头条。

参考：[AIHOT 2026-09-28 更新说明](https://aihot.news/changelog)（报告报纸版式、头版主稿与配图）。

## 当前实现约束

- `buildReport` 从已精选日报合并事件；仅保留公开、可编辑的内容，并排除 reference 来源。
- 周报、月报按既有栏目顺序组织，每栏目分别有数量上限。栏目与条目顺序是现有读者契约，不因头版功能改变。
- 条目代表稿排序已有 `compareRepresentatives`：置顶、一手信源、精选排名分、发布时间。该规则用于事件代表稿，仍只是可复用的自动排序，不等同编辑判断。
- `Report.headline` 是简短期刊抬头。现有测试要求它不被长条目标题替代，因此保留字段原义和现有文案。
- `Item.media` 提供媒体 URL、缩略图、类型和 alt；信息流通过 `/api/media` 安全代理呈现图片。头版不得绕过该代理直接请求远程媒体。
- REST 报告通过 `serializePublicReport` 投影，MCP `get_digest` 又有独立字段白名单；新增主稿必须在两个公开出口都显式序列化，不能靠对象展开意外透传。

## 方案比较

### A. 不增加独立主稿

保留当前栏目列表。维护成本最低，但没有吸收 AIHOT 本次报告头版的核心呈现变化。

### B. 自动生成独立主稿（推荐）

从报告最终入选条目中按既有代表稿排序选一条，以新增的 `coverStory` 字段返回；保留期刊标题和所有栏目顺序。主稿只使用自身条目的图片，安全代理失败或没有图片时退化为纯文字。无需新增人工维护流程，且报告快照与线上报告都可遵循同一计算路径。

### C. 人工指定主稿

增加后台选择及存储字段。编辑控制更精确，但需要新的后台工作流、快照迁移和缺省处理，超出当前可证实的需求，也会把运营维护变成新负担。

## 推荐设计

### 数据与选择

在报告对象上新增可空的 `coverStory`，内容为报告中已经存在的一条 `Item`；不覆盖 `headline`。服务端从最终 `sections` 展平候选，再按现有 `compareRepresentatives` 规则确定一条：置顶优先，其次一手信源、`selectedRankingScore`、发布时间；完全相同的候选以稳定 ID 做确定性收尾。空报告的 `coverStory` 为 `null`。REST 响应通过 `serializePublicItem` 投影该字段；MCP `get_digest` 通过同一公共投影并将其加入明确的报告字段白名单，确保两种接口数据一致且不暴露内部字段。

候选集合不得在最终报告栏目裁剪之后扩张：reference、隐藏、非公开、不合格内容，以及月报栏目上限外的内容均不能成为头版主稿。选择过程不修改 `sections`、`storyCount`、栏目顺序、条目顺序、主题、趋势摘要或报告覆盖日期。多个报告周期共用同一逻辑。

### 图片与呈现

客户端在期刊抬头之后、主题和栏目列表之前展示独立主稿模块。模块标题使用 `coverStory.title`，并展示来源、摘要/精选理由和原文打开入口。若主稿含图片，优先选择自身 `media` 中可用的图片缩略图，否则用该图片的 URL；图片源经现有 `/api/media?url=...` 代理。不得从相关报道或其他条目借图。图片缺失、加载失败或媒体类型不支持时保留完整文字主稿，不显示裂图，也不改变主稿候选。

图像 alt 优先使用媒体自身 alt，缺失时使用主稿标题。窄屏下图片与文字允许纵向排布；不新增第三方图片请求库、不抓取来源网页，也不在导出的 Markdown 中擅自增加不稳定的代理链接。

### 兼容性

`coverStory` 是公开 REST 和 MCP 报告响应中的可选/可空新增字段。旧客户端继续读取 `headline` 和 `sections`；新客户端遇到缺字段或 `null` 时沿用旧版报告版式。REST 与 MCP 均通过公开条目投影序列化主稿，且新增字段采用加法兼容。保留现有 RSS、Markdown 导出、日期导航和报告序列化行为。

## 对抗性审查与边界

1. **分数不等于编辑判断**：复用的是既有代表稿排序，不能对外宣称为“最重要新闻”；模块可标注“本期代表稿”，避免误导。
2. **权威信源不应压过主稿重要性**：既有规则将一手信源放在精选排名分之前。这里只用于选择一个报告内代表稿，不改变各栏目精选顺序；若后续数据证明造成明显失真，再独立评审新的编辑策略。
3. **头版不能绕过精选和栏目限额**：必须从已生成的 `sections` 里选，不从全量数据库重新抓取最高分条目。
4. **图文错配**：图片只能来自 `coverStory` 自身媒体字段；不得拿相关来源的图补位，也不得用另一篇高分文章的图作装饰。
5. **远程媒体安全**：页面只构造本地媒体代理 URL；代理仍负责 DNS、重定向、MIME 和响应大小安全检查。
6. **空值与异常媒体**：无主稿或无有效图片都须稳定退化，不影响报告主体；视频、无效 URL、图片请求失败不能造成空白头版或前端异常。
7. **历史快照一致性**：在由旧日报快照重建周/月报时动态计算主稿，不要求迁移运行数据库，也不把推导字段写回历史数据。
8. **公开投影泄漏**：REST 的 `serializePublicReport` 会展开报告对象，MCP 又维护独立字段白名单；两个出口都必须显式投影 `coverStory`，并证明其不会泄漏内部哨兵字段。

## 验收标准

1. 每种报告周期都只从最终可见栏目条目中选择 `coverStory`；空报告返回 `null`。
2. 选择优先级、完全相同情况下的稳定性有单元测试；reference/隐藏/非公开/栏目限额外项目不会成为主稿。
3. 新字段不改变 `headline`、`sections`、栏目顺序、`storyCount`、趋势或报告覆盖范围；现有短期刊标题测试保持有效。
4. UI 显示主稿标题、来源、摘要/理由及打开入口；图片与主稿绑定，代理 URL 正确；无图、坏图和视频场景均无裂图且文字可读。
5. REST 与 MCP `get_digest` 返回同一公开 `coverStory`；测试证明内部哨兵字段不会穿过任一投影。
6. 日报、周报、月报和旧响应缺少 `coverStory` 时均可渲染；既有 Markdown/RSS/日期导航不回归。
7. 完成相关单元测试、`npm test`、`npm run typecheck`、`npm run build`，并做一次报告页面窄屏/桌面视觉核查。
8. 本设计不授权提交、部署、修改生产数据或生产配置。

## 明确不做

- 不改报告文章的精选、过滤、分数、顺序或每栏目上限。
- 不改简短期刊抬头为文章标题，不用图片替代信息层级。
- 不新增人工头条编辑器、持久化字段或运营工作流。
- 不伪造 4–10 名热点历史曲线；那需要独立的可信时间序列与数据采集设计。
- 不改生产环境、运行数据库或公开 API 的其他字段契约。

## 审核门槛

用户复核本设计后，才编写实施计划；实施计划编写前先进行一次反向审查，重点挑战代表稿的排序依据、报告旧快照兼容与图片代理失败降级。每个实现阶段开始前再次做针对该阶段的对抗性检查。完成本地验证不代表可提交或部署。
