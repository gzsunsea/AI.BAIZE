# AI.BAIZE 内容质量与决策流体验优化设计

## 1. 背景与目标

AI.BAIZE 当前已经具备来源分层、质量评分、热点聚合、事件故事、搜索筛选、阅读工作台和本地/规则摘要能力。本轮优化以内容质量为主轴，面向泛 AI 从业者与内容创作者，提升三件事：

1. 减少参考源、社区噪声、重复事件和缺少证据边界的内容进入策展面；
2. 让精选首页在 30 秒内回答“今天先看什么、为什么值得看”；
3. 让用户从代表事件完成“核验信源 → 阅读原文 → 收藏/处理 → 转为创作素材”的闭环。

本轮不引入付费 API，不重写生产运行库 `data/db.json`，不把分数当作客观真值，也不以降低质量门槛来填满首页。

## 2. 用户与原则

首要用户是泛 AI 从业者和内容创作者。他们需要的不只是新闻标题，而是可判断、可复核、可复用的内容：发生了什么，为什么值得跟进，能否转成工作流或创作角度，还缺什么证据。

核心原则：

- 来源优先级、独立确认和内容实质性共同决定展示层级；
- 事实、系统整理和创作建议必须明确分开；
- 不确定的事件不强行合并，不足的候选不强行补齐；
- `reference` 只用于发现和对照，不进入精选、日报、热点等常规策展面；
- 现有收藏、已读、已处理、问白泽、导出和原文访问能力保持可用。

## 3. 内容质量闸门

### 3.1 展示层级

- **精选**：优先接受 `preferred_x`、`official_first_party`、`expert_rss`，以及满足严格 AI 实质性判定的中文媒体/社区内容。`reference` 不得进入常规精选。
- **跟进线索**：允许单一来源或社区来源，但必须显示“待验证线索”，不与已确认精选混淆。
- **热点事件**：至少需要 2 个独立来源，或 1 个可核验的一手发布加 1 个高质量解读，才显示“多源确认”。同源转载不计作独立来源。

### 3.2 事件与重复

使用现有 canonical URL、标题指纹和事件簇能力：

- 对同一事件提供一个代表条目；关联报道进入阅读工作台；
- 只有明确匹配才合并；不确定的相似标题保留为独立条目；
- 首屏“今日先看”按代表事件去重，不让同一事件占据多个位置。

### 3.3 对外编辑元数据

每条策展内容增加由现有数据计算或生成的编辑元数据：

- `evidenceLevel`：`first_party`、`multi_source`、`expert_analysis`、`single_source` 或 `unverified`；
- `evidenceLabel`：面向用户的短标签，如“一手发布”“多源确认”“专家解读”“待验证线索”；
- `evidenceGaps`：当前仍缺少的验证项；
- `creatorValue`：对创作者或从业者的可复用价值；
- `generatedBy`：`rules`、本地 LLM 或人工编辑；
- 现有 `reason`、`editorialBrief` 继续保留，但不得把自动生成内容伪装成人工判断。

统一内容顺序为“事实 / 为什么值得看 / 对创作者的用处 / 证据边界”。证据不足时显示“信息有限”或具体缺口，不根据标题擅自补写结论。

## 4. 首页决策流

精选页采用“今日先看 → 完整时间线”的首屏结构。

### 4.1 今日先看

- 返回最多 5 个代表事件，实际不足时显示真实数量；
- 按来源可信度、独立确认、时效和对工作流/创作的可复用价值排序；
- 每条显示标题、来源类型、最新时间、独立信源数、验证状态和一句可复用价值；
- 提供进入热点故事或阅读工作台的动作；
- 不展示分数作为唯一解释，分数只用于排序和辅助参考。

### 4.2 完整时间线与主题入口

- 现有日期分组、频道筛选、主题筛选、搜索、密度切换和加载更多继续复用；
- 主题快捷入口以“工具与产品 / 工作流方法 / 创作素材 / 趋势线索”为轻量筛选，不抢占首屏；
- 空状态区分“没有达到质量门槛”和“当前筛选无结果”，提供清除筛选或查看跟进线索的动作；
- 移动端保持单列，首屏信号优先，筛选横向滚动且不造成标题或标签溢出。

### 4.3 失败降级

今日先看接口失败时，降级为现有精选时间线，并提示“今日先看暂不可用”；不阻塞时间线阅读。

## 5. 阅读工作台

阅读工作台采用“证据优先、创作可选”的顺序：

1. 标题、来源、发布时间、来源类型和验证状态；
2. 事实、为什么值得看、对创作者的用处、证据边界；
3. 关联报道与事件时间线；
4. 主动作“阅读原文”，其次为稍后读、标记处理、问白泽、导出和分享。

在核验信息之后增加可选的“创作卡片”，包括标题角度、可引用事实、建议补证和适合的内容形式。创作卡片必须标注“系统整理/生成建议”，每条建议可追溯到对应信源，不能把建议放入事实区。

“问白泽”快捷命令保留，并优先支持比较来源、寻找证据缺口、提炼可复用方法等问题。现有焦点管理、关闭行为、打开原文、关联条目切换和返回位置行为保持不变。

## 6. 技术边界与数据流

### 6.1 服务端

- `server/lib/scoring.js`：扩展质量判定，计算证据等级、验证状态和证据缺口；保持现有评分兼容。
- `server/lib/dedupe.js` 与 `server/lib/experience.js`：复用 canonical URL、标题指纹和事件簇，构建代表事件与关联信源。
- `server/lib/editorial.js`：序列化新的编辑元数据，同时继续隐藏审核、抓取、内部排名和运行时字段。
- `server/index.js`：增加轻量“今日先看”公共结果；现有精选时间线、热点、故事和阅读接口保持兼容。

### 6.2 前端

- `src/types.ts`：增加编辑元数据和今日先看结果类型；
- `src/components/feed/FeedExperience.tsx`：增加首屏信号区、证据标签、创作者价值和有区分的空状态；
- `src/components/reader/ReadingWorkspace.tsx`：调整为证据优先，增加可选创作卡片；
- 现有路由、搜索管线、收藏状态和响应式样式继续复用。

### 6.3 数据流

```text
抓取
  -> 质量候选过滤
  -> canonical / 事件去重
  -> 证据元数据
  -> 今日先看 / 精选 / 热点
  -> 公共序列化
  -> 首页与阅读工作台
```

本轮不强制来源配额：当高质量候选不足时显示不足，不用低质量内容填充。`reference` 在精选、日报、热点等策展面排除，但保留后台诊断与对照能力。

## 7. 错误处理

- 今日先看不可用：提示并降级到精选时间线；
- 本地 LLM 不可用：使用规则摘要，并明确标注“系统整理”；
- 候选不足：显示真实数量和原因，不降低门槛；
- 关联不确定：不合并，保留各自来源；
- 原文打不开：保留摘要、信源、证据边界与问白泽入口，阅读工作台不显示空白；
- API 404 或故事失效：保留现有可返回列表/热点的动作与明确错误状态。

## 8. 验证与验收

### 自动化测试

- 服务端覆盖 `reference` 排除、社区/中文媒体误收与误杀、同源不计独立确认、代表事件去重、证据等级和证据缺口；
- 体验逻辑覆盖今日先看排序、同一事件不重复占位、候选不足和接口降级；
- 前端覆盖证据标签、创作卡片动作、阅读工作台状态和移动端布局约束；
- 回归命令：`npm test`、`npm run typecheck`、`npm run build`。

### 人工验收

- 精选首屏出现 3–5 条真实高价值信号，若不足则如实显示；
- 精选、日报、热点中不出现 `reference` 内容；
- 首屏无连续重复事件；
- 每条首屏内容都能在不打开原文的情况下看懂为什么值得看、证据到哪里为止；
- 关联事件可在阅读工作台内完成代表内容 → 关联信源 → 原文；
- 创作建议与事实分区清晰，且能追溯来源；
- 桌面与移动端均无横向溢出，失败状态仍保留可用阅读动作。

## 9. 非目标

- 本轮不做基于个人行为的核心个性化排序；
- 不新增付费数据源或付费 LLM；
- 不主动访问或自动化任何外部创作者后台；
- 不进行与内容质量和阅读路径无关的大规模架构重构；
- 不把热度、播放量、点赞量或单条爆款替代内容质量判断。
