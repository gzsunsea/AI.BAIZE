# AI.BAIZE 热点榜可用性优化设计

## 问题与证据

线上热点榜长期为空。当前数据检查显示，近 72 小时有 114 条库存内容，其中 101 条通过公开与精选规则、7 条达到精选分阈值，但没有任何精确事件组同时拥有两个当前可验证的独立信源。现有去重还会把同一事件压缩为一个代表条目；热点计算只读取代表条目的实际成员，没有读取事件簇保存的来源元数据，因此真实的历史多源事件也可能被误判为单来源。

空榜在“不能把单条消息说成共识”这一原则上是诚实的，但作为产品入口没有可用内容。目标是在不降低证据标准的前提下恢复入口价值。

## 设计目标

- 继续保证“已确认热点”只由至少两个独立来源支撑。
- 当没有已确认热点时，展示可操作的“正在形成的热点”，明确标注单一来源和待确认状态。
- 修复事件簇来源元数据的读取，让去重后的多源事件可以被正确识别。
- 不改变精选信息流的入选门槛，不把 `reference`、隐藏项、无效 URL、低质量社区噪声放进候选层。
- 保持 API 对外字段白名单，候选内容不暴露原始抓取字段、审核字段或排名内部字段。

## 用户体验

热点页分为两个语义清晰的层级：

1. “已确认热点”：有内容时置于榜单顶部，展示排名、热度、独立信源、最新时间和生命周期。
2. “正在形成的热点”：当确认榜不足以填满入口，展示最多 5 条近期精选候选。每条显示“待确认”标签、来源、发布时间和证据缺口；文案明确说明这不是多源共识。

确认榜为空时，页面不再只显示一张空状态卡，而是保留规则说明，先解释“近 72 小时暂无多源确认事件”，再呈现候选层。候选层为空时才显示原有空状态，并补充可查看精选时间线的入口。

## 数据与排序

`buildHotTopics` 保留现有 `items` 字段作为已确认热点，新增 `candidates` 字段和可选的 `availability` 摘要。

- 事件来源集合由三部分合并：公开有效的实际成员来源、事件簇保存的 `sources`、代表项保存的 `duplicateSources`。
- 来源按稳定身份去重；`duplicateCount` 只能表示重复观察次数，不能单独增加独立来源数。
- `items` 只有来源集合不少于 2 个时才进入确认榜；原有人工置顶单来源例外改为候选层，避免与“多源确认”标题冲突。
- 候选从近 72 小时内通过 `isSelectedFeedEligible` 的公开精选内容生成，按精选排序分、来源层级和时效排序；同一来源最多 2 条，避免单一来源占满候选层。
- 已进入确认榜的事件和重复候选不再进入候选层；候选最多 5 条。
- 候选使用 `evidenceMeta` 的 `single_source` 或 `unverified` 状态，并提供“独立信源仍不足”等证据缺口。

## API 契约

`GET /api/public/hot-topics` 返回：

- `items`: 已确认热点，保持现有字段兼容。
- `candidates`: 待确认候选，使用公开条目字段，附带 `status: "emerging"`、`availability: "candidate"` 和证据元数据。
- `availability`: `confirmed`、`candidate` 或 `empty`，用于前端选择准确空状态。

候选与确认榜都经过现有公开序列化；不返回 `raw`、`hidden`、`priorityTier`、`duplicateSources`、`duplicateCount` 等内部字段。

## 错误处理与降级

- API 成功但没有确认热点时仍返回 200，并返回候选或明确的 `empty` 状态。
- 热点计算失败时保留错误状态和重试入口，不把精选信息流误当成热点榜数据。
- 候选不能证明事件已经被确认，候选文案不得使用“共识”“多源确认”等表述。
- 详情页沿用公开条目过滤；只有真实可见的事件来源才进入时间线。

## 测试与验收

- 构造一个只有单代表项、但事件簇 `sources` 含两个独立来源的案例，确认它进入 `items`。
- 构造只有一个精选来源的近期内容，确认它进入 `candidates` 而不是 `items`。
- 确认 `reference`、隐藏、无效 URL 和低质量社区内容不会进入任一公开层。
- 确认候选按来源限额排序且不重复事件。
- 确认热点 API、前端类型和空状态文案对新字段兼容。
- 运行 `npm test`、`npm run typecheck`、`npm run build`，并在生产环境检查热点 API 为 JSON、内容非空或返回明确 `empty`，不出现假 200 HTML。
